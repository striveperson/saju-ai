# PR

PR 본문은 리뷰어가 diff 를 읽기 전에 맥락을 잡는 자리다.
diff 와 CI 가 이미 말하는 것을 옮겨 적으면 정작 읽어야 할 왜가 묻힌다.

상위 규칙은 [CLAUDE.md](../../../CLAUDE.md) 의 Git 절이다.
제목 규격은 `commit` 스킬의 type 과 scope 표를 그대로 쓴다.

## 순서

### 1. 브랜치 확인

`main` 이면 멈춘다. `main` 에 직접 push 하지 않는다.
`feature/<요약>`, `fix/<요약>`, `chore/<요약>` 중 맞는 것으로 옮길 것을 제안하고 승인을 받는다.

### 2. 커밋과 push

로컬 `git` 으로 한다. 커밋 메시지는 `commit` 스킬을 따른다.
`push_files` MCP 도구로 커밋하지 않는다. 그 도구는 로컬 워킹트리를 모른다.

### 3. 본문 작성

`git diff main...HEAD --stat` 과 `git log main..HEAD` 를 읽고 아래 규칙으로 쓴다.

### 4. 생성

`github` MCP 의 `create_pull_request` 를 쓴다. `gh` CLI 를 쓰지 않는다.
base 는 `main` 이다. 커밋이 하나면 그 제목을 PR 제목으로 쓴다.

## 본문

### 요약은 항상 쓴다

`## 요약` 으로 시작한다. 한두 문단이면 된다.

이 변경이 없으면 무엇이 문제인지를 쓴다. 무엇을 바꿨는지는 diff 가 말한다.
판단이 갈릴 수 있었던 지점이 있으면 왜 그쪽을 골랐는지 한 줄 남긴다.

자명한 PR 은 여기서 끝난다. 절을 더 만들지 않는다.

### 나머지는 diff 를 보고 판단한다

조건에 맞을 때만 `##` 절로 더한다. 해당 없으면 절 자체를 만들지 않는다.

| 절                    | 조건                               | 내용                                                                                                 |
| --------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `## 커밋`             | 커밋이 셋 이상                     | 커밋마다 한 줄. 리뷰 순서를 잡아준다                                                                 |
| `## 도메인 규칙`      | `apps/web/src/lib/saju/**` 변경    | 근거가 된 `docs/05-saju-domain-rules.md` 장 번호나 ADR 번호. 유파 옵션에 영향이 있으면 어느 옵션인지 |
| `## Breaking Change`  | 호환성이 깨짐                      | 무엇이 깨지고 호출부를 어떻게 바꾸는지. 커밋 본문의 `BREAKING CHANGE` 와 같은 내용이어야 한다        |
| `## 스크린샷`         | UI 변경                            | 첨부. 없으면 "스크린샷 첨부 필요" 로 남긴다                                                          |
| `## 확인이 필요한 것` | 판단이 안 선 지점이 있음           | 리뷰어에게 묻고 싶은 것. 얼버무리지 말고 질문으로 쓴다                                               |
| `## 관련 이슈`        | 커밋이나 브랜치 이름에 번호가 있음 | `Closes #42`, `Refs #17`                                                                             |

`## 도메인 규칙` 이 이 저장소에만 있는 절이다.
사주 계산은 왜 그 값인지가 코드에 남지 않는다.
엔진을 건드렸는데 근거가 없으면 리뷰어가 판단할 방법이 없다.

## 넣지 않는 것

- 파일 목록과 변경 내용 나열. PR 페이지가 커밋과 diff 를 이미 보여준다
- 검증 체크리스트. `pnpm typecheck`, `lint`, `test` 는 통과해야 push 하는 것이고
  `pre-commit-check.sh` 가 이미 막는다
- 규약 준수 체크박스. 시크릿과 개인정보, 문서 동시 변경 같은 것은
  훅과 lint 가 강제한다. 자기 신고로 대신하지 않는다
- 테스트 방법. 리뷰어가 직접 재현해야 할 절차가 있을 때만 쓴다.
  대개는 테스트 코드가 그 자리다
- 되돌리기. 단순 revert 로 안 되는 경우에만 쓴다
- 절 수로 성의를 재는 것. 빈 절이나 "해당 없음" 을 남기지 않는다

## 경계

- PR 생성까지 한다. 병합은 별도 지시가 있을 때만 한다
- 리뷰 코멘트는 `pull_request_review_write` 로 pending review 를 만들고
  `add_comment_to_pending_review` 로 채운 뒤 제출한다
- 브랜치 보호 규칙은 아직 걸려 있지 않다. 규칙이 없다고 `main` 에 직접 올리지 않는다
