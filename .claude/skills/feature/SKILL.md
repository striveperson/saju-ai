# 기능 구현 다섯 단계

이 저장소에는 다섯 단계가 다 있는데 흩어져 있다.
ADR 이 설계를, [docs/06](../../../docs/06-code-working-rules.md) 4장이 테스트를,
`saju-engine-validator` 가 품질을, 훅과 내장 명령이 보안을 맡는다.
흩어져 있으면 어떤 턴은 지나고 어떤 턴은 건너뛴다.

이 스킬이 그 순서다. 새 도구를 만드는 것이 아니라 이미 있는 것을 부르는 차례를 정한다.

## 왜 이 순서인가

단계마다 막는 실패가 다르다.

| 단계 | 이 단계가 없으면 |
| --- | --- |
| 계획 | 짐작한 전제 위에 구현이 쌓인다. 다 만든 뒤에 전제가 틀린 것을 안다 |
| 설계 | 왜 그렇게 정했는지가 코드에 안 남는다. 같은 논의가 반복된다 |
| 테스트 | 무엇이 되면 끝인지가 없다. "동작하게 해줘" 는 매번 다시 물어야 한다 |
| 품질 | 구현한 맥락에서 스스로 확인해 방금 한 착각을 한 번 더 한다 |
| 보안 | 시크릿과 생년월일시가 조용히 로그와 커밋에 남는다 |

앞 단계를 건너뛰면 뒤 단계가 그 값을 근거로 쓴다.
설계 없이 구현하면 테스트가 틀린 설계를 고정하고, 그 테스트가 통과하므로 품질 검토가 넘어간다.

## 안 도는 경우

오타, 한 줄짜리 변경, 문서만 고치는 것에는 쓰지 않는다.
docs/06 머리말이 "속도보다 신중함 쪽으로 기운 규칙이다" 로 적고 같은 예외를 둔다.

부를 때만 적용된다. 스스로 판단해 시작하지 않는다.
"복잡한 기능이면 자동으로" 를 만들면 복잡의 기준을 매번 다시 재게 되고,
그것이 docs/06 4장이 "동작하게 해줘" 를 나쁜 성공 조건으로 든 이유와 같은 부류다.

엔진은 잊어도 막힌다. `saju-validate-gate.sh` 가 4단계를 강제한다.

## 1. 계획

전제를 말로 적는다. 확신이 없으면 묻는다. 요청이 두 가지로 읽히면 둘 다 내놓는다.
docs/06 1장이다.

받은 요청을 검증 가능한 목표로 바꾼다. 여러 단계면 계획을 짧게 적는다.

```
1. [단계] / 확인: [무엇으로 확인하는가]
2. [단계] / 확인: [무엇으로 확인하는가]
```

수치와 경계를 추론으로 적지 않는다. 먼저 돌려 확인한다.
결론이 되는 값만 보지 말고 그 값을 만드는 중간값도 본다.
같은 답이 나온다고 같은 경로로 온 것은 아니다.

넘어가는 조건은 전제가 적혔고 성공 조건이 확인 방법과 함께 나온 것이다.

## 2. 설계

구조나 기술 결정일 때만 돈다. 아니면 건너뛰고 그렇게 적는다.

결정이면 ADR 을 코드보다 먼저 쓴다. 위치는 `docs/adr/`,
형식은 [docs/00](../../../docs/00-documentation-guide.md) 4장이다.

기존 결정을 바꾸는 것이면 그 ADR 을 수정하지 않는다.
새 ADR 을 쓰고 기존 것의 상태를 대체됨으로 바꾼다.

채택하지 않기로 한 것도 적는다. 같은 논의가 반복되는 것을 막는 것이 ADR 의 값어치다.

넘어가는 조건은 트레이드오프 절에 포기한 것이 적힌 것이다.
장점만 있으면 그 ADR 은 미완성이다.

## 3. 테스트

성공 조건을 테스트로 옮긴다.

| 받은 요청 | 먼저 쓸 것 |
| --- | --- |
| 검증을 추가해줘 | 잘못된 입력에 대한 테스트 |
| 버그를 고쳐줘 | 버그를 재현하는 테스트 |
| X 를 리팩터링해줘 | 전후로 통과할 기존 테스트 확인 |

엔진이면 [docs/05](../../../docs/05-saju-domain-rules.md) 10장 목록에서 해당 항목을 고른다.
경계 케이스는 선택이 아니다.

화면이면 `docs/mockups/` 의 HTML 이 정답지다. 목업에 있는 값을 그대로 기대값으로 쓴다.

넘어가는 조건은 테스트가 먼저 실패하는 것을 본 것이다.
구현 뒤에 쓴 테스트는 무엇을 잡는지 알 수 없다.
이미 통과하는 단언은 지워도 아무것도 실패하지 않는다.

## 4. 품질

구현과 다른 맥락에서 대조한다. 스스로 확인하지 않는다.

| 바뀐 자리 | 부를 것 |
| --- | --- |
| `apps/web/src/lib/saju/**` | `saju-engine-validator` |
| `src/components/**`, `src/features/**`, `src/routes/**` | `saju-screen-validator` |
| 둘 다 | 둘 다. 각각 자기 범위만 본다 |

부르기 전에 기계가 잡는 것을 털어낸다. 검증기에 보낼 것이 아니다.

```
pnpm --filter web exec vitest run
pnpm --filter web typecheck
pnpm --filter web lint
```

넘어가는 조건은 차단 0 이다. 기록이 남아 있어도 통과다.
지적을 0 으로 만들려 하면 고칠 때마다 새 검증이 붙어 끝나지 않는다.

기록 항목이 쌓였으면 `validate-loop` 스킬로 따로 훑는다. 여기서 처리하지 않는다.

## 5. 보안

내장 `/security-review` 를 부른다. 그 다음 이 저장소만의 넷을 눈으로 본다.

- 시크릿이 코드에 있는가. Supabase 키, Gemini API 키, GitHub PAT 은 환경변수로만 들어온다
- 생년월일시가 로그에 남는가. 개인정보다
- 해석 캐시 키에 사용자를 식별할 수 있는 것이 들어갔는가.
  키는 팔자, 판정 결과, 계산 옵션, 프롬프트 버전, 모델 버전의 해시다
- 공유 링크가 기본으로 만들어지는가. 사용자가 명시적으로 생성해야 존재한다

커밋 메시지도 본다. 픽스처를 다루는 커밋에서도 생년월일시 값 자체를 옮기지 않는다.

넘어가는 조건은 넷 다 아니오인 것이다.

## 보고

끝나면 단계마다 무엇을 했는지 한 줄씩 적는다. 건너뛴 단계는 왜 건너뛰었는지 적는다.

```
1 계획   전제 3개, 성공 조건 2개
2 설계   건너뜀. 구조 결정이 아니다
3 테스트 PaljaTable.test.tsx. 목업 값으로 먼저 실패 확인
4 품질   saju-screen-validator. 차단 0, 기록 2
5 보안   /security-review 통과. 넷 다 해당 없음
```

조용히 빼지 않는다. 건너뛴 것이 보이지 않으면 이 순서를 도는 의미가 없다.

## 경계

- 커밋과 push 는 하지 않는다. 끝나면 `commit` 스킬로 메시지만 낸다
- 기록 항목을 고치지 않는다. `validate-loop` 이 그 자리다
- 검증기는 읽기만 한다. 무엇을 고칠지 정하는 것은 이 순서를 도는 쪽이다
- 단계를 앞당기지 않는다. 4단계 지적을 미리 짐작해 3단계에서 고치면
  검증기가 볼 것이 없어지고 그 단계가 통과인지 비어 있는지 구분되지 않는다
