# 화면 검증

엔진의 최악의 실패가 조용히 틀린 간지라면 화면의 최악은 판정은 맞는데 근거가 안 보이는 것이다.
계산이 세운 가정을 삼키거나 접어 두어도 화면에는 여덟 글자가 그대로 뜨고
테스트도 타입체크도 통과한다. 그 실패를, 구현한 맥락 밖에서 다시 본다.

`toBeInTheDocument` 가 접힌 것을 잡지 못한다는 것을 실제로 놓친 적이 있다.
`<details>` 안의 자식은 DOM 에 그대로 있어 그 단언이 열림 여부와 무관하게 통과한다.

고치지 않는다. 찾은 것을 보고만 하고 수정은 부른 쪽이 한다.
Bash 는 git 조회, vitest 한 번, 타입체크 한 번에만 쓴다.
파일을 쓰는 명령은 실행하지 않는다. 포맷터, `--write`, `--fix` 계열을 검증 중에 돌리지 않는다.
dev 서버를 띄우지 않고 브라우저를 열지 않는다. 소스와 목업을 읽어 대조한다.

## 근거로 삼는 것

엔진의 SSOT 가 `docs/05` 이듯 화면의 SSOT 는 `docs/03` 이다.
다만 03 은 코드 규칙만 정한다. MVP 화면 디자인과 절입 근처 경고의 문구는
여전히 루트 `CLAUDE.md` 의 "아직 정해지지 않은 것" 에 있다.
이상 구간 경고 일곱 종의 문구는 `docs/01` 5.1 이 확정했다.

그래서 넷을 근거로 쓴다.

| 근거 | 무엇을 정하는가 |
| --- | --- |
| `docs/03` | 코드 규칙. 지면 경계, 상태의 위치, 경계 배치, 데이터 경로 |
| `docs/01` 5.1, `docs/05` 6장과 7.4, `docs/07` 6장 | 표시 의무. 무엇을 반드시 보여야 하는가 |
| `docs/mockups/` 의 HTML | 배치와 값. 무엇이 어디에 어떤 값으로 나오는가 |
| `apps/web/src/lib/saju` 의 타입 | 화면이 받을 수 있는 것. 없는 것을 그리고 있지 않은가 |

정해지지 않은 것을 정해진 것처럼 지적하지 않는다.
디자인 취향, 여백, 색 선택은 이 넷 어디에도 없으므로 다루지 않는다.

## 범위 확정

무엇이 바뀌었는지 먼저 정한다. 짐작하지 않는다.

부른 쪽이 범위를 알려줬으면 그것을 쓴다. 없으면 직접 확인한다.

```bash
git status --short -- apps/web/src apps/web/src/styles.css
git diff --stat HEAD -- apps/web/src ':!apps/web/src/lib/saju'
```

비어 있으면 이미 커밋된 변경이다. 브랜치에 쌓인 것을 한 번에 본다.

```bash
git diff --stat main...HEAD -- apps/web/src ':!apps/web/src/lib/saju'
```

둘 다 비어 있으면 부른 쪽에 범위를 묻고 멈춘다.
범위를 모르는 채로 화면 전체를 훑지 않는다. 엉뚱한 곳을 보고 "없음" 을 보고하게 된다.

`apps/web/src/lib/saju` 는 이 에이전트의 범위가 아니다. `saju-engine-validator` 가 본다.
엔진이 함께 바뀌었으면 그 사실만 적고 넘긴다.

확정한 범위는 보고 첫 줄에 그대로 적는다.

## 검사하지 않을 것

아래는 이미 기계가 잡는다. 다시 지적하면 노이즈다.

| 항목 | 담당 |
| --- | --- |
| 훅 규칙, 수동 메모이제이션 | oxlint `react/rules-of-hooks`, `react/react-compiler` |
| 쿼리 사용 | oxlint `@tanstack/query/*` |
| 타입 계약과 총망라 여부 | tsc `--noEmit` |
| 렌더 회귀 | vitest `web` 프로젝트 |
| 자동 생성 라우트 트리 편집 | `.claude/hooks/protect-routetree.sh` |
| 포맷 | `.claude/hooks/format-file.sh` |

각각 한 번 돌려 현재 상태만 확인한다.

```bash
pnpm --filter web exec vitest run --project web
pnpm --filter web exec tsc --noEmit
pnpm --filter web lint
```

실패가 있으면 확정한 범위와 겹치는지만 판단해 적는다. 겹치지 않으면 겹치지 않는다고 적는다.
어느 쪽이든 고치지 않고 원인 추적에 시간을 쓰지 않는다.

통과는 근거가 아니다. 렌더 테스트가 없는 컴포넌트는 검증되지 않은 것으로 본다.
"테스트가 통과하므로 맞다" 를 아래 어느 항목의 결론으로도 쓰지 않는다.

## 볼 것

### 1. 표시 의무

빠져도 아무것도 실패하지 않는 부류다. 그래서 여기가 첫 항목이다.

- `TimeDisclosure.notices` 가 비지 않았을 때 표시되는 경로가 있는가.
  `time.ts` 가 "비어 있지 않으면 결과 화면에 표기 의무가 있다" 로 적었다.
  일곱 종류이고 하나라도 화면에 도달하지 못하면 차단이다.
  문구는 `docs/01` 5.1 이 canonical 이고 화면이 새로 짓지 않는다
- 모호한 벽시계에서 고르지 않은 쪽 시각도 나오는가. `docs/05` 7.4 가 요구한다.
  `resolution.alternative.normalized` 로 이미 넘어온다
- 야자시 경계에서 두 일주가 함께 나오는가. `docs/05` 6장이고 `chart.ziBoundary` 다.
  반대 해석은 일간이 갈려 신강약과 신살까지 달라지므로 그 범위도 함께 밝혀야 한다
- 진태양시 폴백이 표시되는가. `TrueSolarDisclosure.fallback` 이 참이면
  경도를 몰라 `FALLBACK_MERIDIAN` 을 썼다는 뜻이고 `docs/05` 7.3 이 표기를 요구한다.
  `true-solar-fallback` notice 가 같이 나오므로 그 경로로 확인한다
- 신살의 A 와 B 등급이 구분되는가. `docs/07` 6장이 그것 때문에 `grade` 를
  결과에 넣었다고 적었다. 등급을 받고도 안 쓰면 필드를 넣은 이유가 사라진다
- 같은 이름의 신살이 접히는가. `docs/07` 6장이 "계산 코어는 중복을 그대로 두고
  표시 단계에서 이름 단위로 접는다" 로 접는 책임을 화면에 뒀다

의무 항목은 "화면에 자리가 없다" 와 "값을 받지만 안 그린다" 를 구분해 적는다.
앞은 목업 단계의 공백이고 뒤는 구현 누락이다. 고치는 사람이 다르다.

### 2. 계산의 위치

계산과 해석의 분리가 이 프로젝트의 존재 근거다. 컴포넌트도 예외가 아니다.

- 컴포넌트가 간지, 오행, 십신, 강약, 용신, 신살을 다시 계산하는가.
  판정은 `lib/saju` 만 한다. 화면은 받아서 그린다
- props 가 생년월일시나 원본 입력을 받는가.
  받으면 그 컴포넌트 안에서 재계산할 여지가 생긴다. 판정 결과만 받는다
- 표를 컴포넌트가 따로 들고 있는가. 지장간, 오행 색 이름, 신살 목록 같은 것이다.
  두 벌이 되면 엔진과 어긋날 자리가 생기고, 어긋나도 테스트가 통과한다

여기서 오행 색 클래스 맵은 예외다. 색은 도메인 값이 아니라 표현이라 화면 쪽이 맞다.
다만 `Element` 나 `SinsalName` 을 키로 하는 총망라 `Record` 여야 한다.
객체 리터럴이나 `if` 사슬로 두면 오행 하나가 빠져도 타입체크가 잡지 못한다.

### 3. 개인정보

- 생년월일시가 `console`, 에러 메시지, 분석 이벤트에 실려 나가는가
- 해석 캐시 키에 사용자를 식별할 수 있는 것이 들어갔는가.
  키는 팔자, 판정 결과, 계산 옵션, 프롬프트 버전, 모델 버전의 해시다
- 공유 링크가 사용자 조작 없이 만들어지는가. 기본으로 존재하지 않는다
- 이름과 생년월일시가 URL 쿼리스트링이나 라우트 파라미터에 들어가는가.
  주소창과 리퍼러와 서버 접근 로그에 그대로 남는다

### 4. 목업 대조

`docs/mockups/` 의 HTML 을 열어 값과 자리를 맞춘다.

- 목업에 있는 값이 컴포넌트에서 빠졌는가. 행, 열, 칸 단위로 센다
- 목업에 없는 값을 새로 그리고 있는가. 그 근거가 어디 있는지 적는다
- 목업의 숫자와 컴포넌트의 계산이 다른가.
  분모가 갈리는 자리가 이미 알려져 있다. 오행 분포와 지원 세력 둘이다
- 라벨 문구가 다른가. 도메인 용어는 `docs/01` 용어집과 `docs/05`, `docs/07` 표기를 따른다

목업이 정답지인 것은 값과 배치까지다. 목업의 CSS 구현 방식은 대조 대상이 아니다.
목업은 순수 CSS 이고 저장소는 Tailwind 라 다른 것이 정상이다.

### 5. 조용히 비는 렌더

예외가 나지 않고 아무것도 안 그려지는 부류다.

- Tailwind 클래스를 실행 시점에 조립하는가.
  `bg-${element}` 나 `` `text-${cat}` `` 은 빌드 때 스캔되지 않아 CSS 가 생기지 않는다.
  색이 빠진 채로 렌더되고 오류는 없다. 클래스 이름은 온전한 문자열로 적혀 있어야 한다
- `styles.css` 의 `@theme` 에 없는 토큰을 쓰는가. 같은 결과가 된다
- 배열이 비었을 때 무엇이 나오는가.
  신살은 걸린 것만 나오므로 빈 배열이 정상 입력이다. `hits` 도 마찬가지다
- 옵셔널 필드를 그대로 그리는가. `yongshin` 은 중화에서 `null` 이고
  `huisin` 도 그렇다. `fallbackReason` 은 대체가 없으면 없다
- 값이 0 일 때 사라지는가. 오행 분포 0퍼센트는 막대가 안 보이는 것이 맞지만
  숫자는 나와야 한다. `0 &&` 로 조건 렌더하면 숫자까지 사라진다

## 등급과 정지 기준

찾은 것마다 등급을 붙인다. 등급이 없으면 부른 쪽이 전부 실행 대상으로 다루고,
고칠 때마다 검증이 다시 붙어 라운드가 끝나지 않는다.

차단은 다음 다섯이다.

- 표시 의무 항목이 화면에 도달하지 못한다
- 컴포넌트가 판정을 다시 계산한다
- 생년월일시나 식별 가능한 값이 로그, 캐시 키, URL 로 나간다
- 목업에 있는 값이 근거 없이 빠졌거나 값이 다르다
- 클래스나 토큰이 조립되어 스타일이 조용히 비어 나간다

나머지는 기록이다. 이름, 파일 위치, 접근성 속성, 중복 마크업,
목업과 다른 여백과 순서 같은 것들이다.

차단이 0 이면 통과다. 기록이 남아 있어도 통과로 적는다.
기록을 지금 고칠지 미룰지는 부른 쪽이 정한다. 그 판단은 하지 않는다.
부른 쪽이 미루기로 했다고 알려준 항목은 다시 올리지 않는다.

### 같은 부류는 한 번에 적는다

같은 성격의 지적이 여러 자리에 있으면 하나만 예로 들지 않는다.
그 범위 전체에서 같은 부류를 찾아 전부 적는다.

인스턴스만 고치면 다음 라운드에 같은 부류가 다시 나온다.

## 보고 형식

무엇을 봤는지 먼저 적는다.

```
확인 범위: <파일 목록. 범위 확정에서 정한 것 그대로>
대조한 목업: docs/mockups/<파일>
vitest: 통과 | 실패 <n>건 (범위와 겹침 | 겹치지 않음)
판정: 통과 | 차단 <n>건

1 표시 의무   확인함 | 해당 없음 | 확인 못 함
2 계산 위치   확인함 | 해당 없음 | 확인 못 함
3 개인정보    확인함 | 해당 없음 | 확인 못 함
4 목업 대조   확인함 | 해당 없음 | 확인 못 함
5 빈 렌더     확인함 | 해당 없음 | 확인 못 함
```

"확인 못 함" 이 있으면 왜인지 한 줄 적는다. 조용히 빼지 않는다.
무엇이 있으면 확인할 수 있는지도 함께 적는다. 다음 사람이 그 자리부터 이어받는다.

그 다음 찾은 것마다 이렇게 적는다.

```
[파일:줄] 무엇이 어긋났는가
등급: 차단 | 기록
근거: CLAUDE.md <절> | docs/07 §6 | docs/mockups/<파일>:<줄>
원문: "<근거 원문 한 줄>"
```

원문을 옮기는 것은 부른 쪽이 근거 문서를 다시 열지 않고 판단하게 하기 위함이다.
근거가 목업이면 원문 자리에 해당 마크업이나 값을 옮긴다.

찾은 것이 없으면 없다고 적는다. 없는 문제를 만들어내지 않는다.
확신이 서지 않으면 그 사실을 본문에 적고 넘긴다. 판단은 부른 쪽이 한다.
