# ADR 0005. 사주풀이는 규칙 엔진이, 사주 해석은 LLM 이 맡는다

- 상태: 채택(Accepted)
- 날짜: 2026-08-05

## 배경

프로젝트 이름에 ai 가 들어가지만, LLM 을 어디까지 쓸 것인지는 정해진 바 없다.
사주팔자를 뽑는 것부터 해석 문장을 쓰는 것까지 전부 LLM 에 맡길 수도 있고,
계산만 코드로 하고 해석을 맡길 수도 있다.

## 결정

두 단계를 나눈다.

1. 사주풀이(결정론): 생년월일시에서 사주팔자를 뽑고, 오행 분포와 십신 구성, 신강약, 용신, 신살을
   규칙으로 판정한다. `apps/web/src/lib/saju` 의 순수 함수가 전부 담당한다.
2. 사주 해석(생성): 1단계가 낸 판정 결과를 LLM 에 넘겨 그것이 어떤 의미인지를 문장으로 풀게 한다.
   모델은 Gemini Flash Lite 계열을 쓴다.

프롬프트에는 계산 결과만 넣는다. 생년월일시 원본을 넣어 LLM 이 재계산하게 두지 않는다.

## 이유

- LLM 이 간지나 오행 강약을 직접 계산하면 같은 사주에 다른 결과가 나온다.
  사주는 입력이 같으면 결과가 같아야 하는 영역이다. 재방문했을 때 답이 달라지면 서비스를 믿을 수 없다.
- 계산을 코드가 확정하면 화면에 근거를 함께 보여줄 수 있다.
  "수기 과다, 정관 2개" 같은 판정을 제시하고 그에 대한 설명을 붙이는 구조가 된다.
- 판정 결과가 확정적이므로 그것을 해시해 해석문을 캐싱할 수 있다([ADR 0011](0011-single-prompt-no-streaming.md)).
- LLM 은 잘하는 일만 맡는다. 맥락을 반영한 자연어 설명이 그것이다.

## 트레이드오프 / 대안

- 대안 1: LLM 창작 중심. 팔자와 오행 분포만 넣고 해석 전체를 맡긴다.
  구현이 빠르고 문장이 풍부하지만 재현성이 없고 근거를 제시할 수 없다.
  사실이 아닌 내용을 만들어낼 위험도 남는다.
- 대안 2: 규칙 엔진 전용. 판정별 문구를 미리 쓰고 조합한다. 비용이 0 이고 완전히 오프라인이지만
  문장이 템플릿 티가 나고 사용자가 금방 질린다.
- 규칙을 직접 정의해야 하므로 도메인 조사 비용이 든다.
  이 비용은 `/Users/mychoi/f-lab/saju` 의 도메인 문서를 승계해 상당 부분 줄인다.
- MVP 규칙 범위를 좁게 시작한다. 신살은 채택 등급 A·B 만 다루고 C 는 넣지 않는다.

## 영향

- 계산 엔진의 출력 타입이 곧 API 계약이자 프롬프트 계약이 된다.
  출력 타입을 바꾸면 캐시 키가 달라지고 프롬프트도 바뀐다.
- 프롬프트에 원본 생년월일시를 넣지 않는다는 제약을 CLAUDE.md 최상단에 못 박는다.
  이것이 무너지면 이 ADR 전체가 무의미해진다.
- 계산 규칙의 단일 진실 공급원은 [`05-saju-domain-rules.md`](../05-saju-domain-rules.md) 다.
