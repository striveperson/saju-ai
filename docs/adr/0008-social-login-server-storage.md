# ADR 0008. 소셜 로그인으로 식별하고 사주를 서버에 저장한다

- 상태: 채택(Accepted)
- 날짜: 2026-08-05

## 배경

생년월일시와 해석 결과를 어디에 둘지 정해야 한다.
[ADR 0003](0003-spa-bundle-for-app.md) 에서 앱이 오프라인으로 계산까지 끝내는 구조를 택했으므로
기능 동작만 놓고 보면 서버에 아무것도 저장하지 않아도 된다.

다만 생년월일시는 개인정보다. 다른 정보와 결합하면 개인을 식별할 수 있고,
이름을 함께 받으면 식별 가능성이 더 분명해진다. 저장 여부는 법적 의무를 동반하는 결정이다.

## 결정

1. 소셜 로그인으로 사용자를 식별한다.
2. 사주 프로필(이름, 생년월일시, 성별, 경도, 계산 옵션)을 서버에 저장한다.
3. 저장된 사주는 URL 로 공유할 수 있다. 공유 정책은 [ADR 0009](0009-share-link-policy.md) 에서 정한다.
4. LLM 해석은 팔자와 판정 결과를 해시한 키로 별도 캐싱해 사용자 데이터와 분리 보관한다.
   해석 캐시에는 사용자를 식별할 수 있는 정보가 들어가지 않는다.
5. 로그인 없이도 계산과 결과 확인까지는 되게 한다. 저장과 공유 시점에만 로그인을 요구한다.

## 이유

- 기기가 바뀌어도 이력이 유지되고 웹과 앱이 같은 데이터를 본다.
  가족이나 지인 사주를 여러 개 저장해두고 다시 보는 사용 방식이 사주 서비스의 재방문 동기다.
- 공유가 제품의 확산 경로다. 공유하려면 사주가 서버에 있어야 한다.
- 해석 캐시를 사용자 데이터와 분리하면 캐시는 개인정보가 아니게 된다.
  같은 사주를 여러 사람이 조회해도 캐시가 공유되어 AI 호출이 줄어든다.

## 트레이드오프 / 대안

- 대안 1: 무로그인 + 로컬 저장. 서버에 개인정보가 남지 않아 처리방침 부담이 가장 적고 진입 장벽이 없다.
  기기를 바꾸면 이력이 사라지고 공유를 구현할 수 없다.
- 대안 2: 완전 무저장. 서버가 LLM 프록시 역할만 한다. 인프라가 가장 가볍지만
  해석 캐시가 없어 같은 사주를 볼 때마다 AI 호출 비용이 든다.
- 첫 사용에 로그인 장벽이 생긴다. 계산과 결과 확인까지는 로그인 없이 열어두어 완화한다.
- 개인정보 처리방침, 수집·이용 동의, 회원탈퇴 시 파기 절차를 갖춰야 한다.
- 소셜 로그인 공급자에 카카오나 구글을 넣으면 iOS 앱은 App Store 지침 4.8 에 따라
  Apple 로그인도 함께 제공해야 한다. 이 의무는 [ADR 0010](0010-supabase-auth-and-db.md) 에서 다룬다.
- 유출 시 피해 범위가 무저장 방식보다 크다. 권한 설계를 테이블마다 명시하고 테스트로 검증한다.

## 영향

- 공유 페이지는 인증 없이 열리는 경로다. 노출 범위를 따로 정해야 한다([ADR 0009](0009-share-link-policy.md)).
- 공유 페이지를 SSR 로 렌더링하면 OG 미리보기를 만들 수 있다.
  [ADR 0003](0003-spa-bundle-for-app.md) 에서 웹을 SSR 로 남긴 결정이 여기서 값을 한다.
- 스키마 초안은 `saju_profiles`, `share_links`, `interpretation_cache` 세 테이블이다.
