# ADR 0014. 절기는 계산해 번들하고 KASI 는 교차검증에만 쓴다

- 상태: 채택(Accepted)
- 날짜: 2026-08-08

## 배경

[ADR 0006](0006-manseryeok-and-time-correction.md) 은 절기 시각과 음력 변환에 KASI 데이터를 쓴다고
정했지만 조달 방식은 비워두었다. 검증 케이스 24개 중 20개가 이 데이터를 기다리고 있어
계산 엔진 구현이 여기서 막힌다.

공공데이터포털 API 를 실제로 호출해 두 가지를 확인했다.

| 서비스      | 주는 것                                      | 지원 연도      |
| ----------- | -------------------------------------------- | -------------- |
| 특일 정보   | 24절기 날짜와 절입 시각(`HH:mm`)             | 2000~2028      |
| 음양력 정보 | 음양 변환, 윤달 구분, 간지(일진, 세차, 월건) | 1600 이전~2050 |

절기가 29년치뿐이다. 사주 서비스의 주 사용자층이 1960년대생이므로 이 범위로는 성립하지 않는다.
KASI 월력요항도 2021~2028 만 공개되어 있고 과거 아카이브가 없다.
국내에 1900~2100 을 덮는 공식 절기 데이터는 없다.

대조 과정에서 KASI 데이터의 결함도 드러났다.

- 대한 2011 은 날짜가 하루 밀려 있다. 소한에서 대한까지 간격이 15.72일인데
  근일점 부근이라 14.7일이어야 하는 구간이다.
- 입동 2011 은 입동 2012 의 시각이 그대로 복사되어 있다. 2012년 값은 계산과 정확히 일치한다.
- 하지 2015 는 20분 어긋난다.
- 대한 2019 는 `17:60` 으로 존재하지 않는 시각이다.
- `sunLongitude` 필드가 696건 중 230건에서 결측이다.

## 결정

KASI 를 데이터 출처가 아니라 교차검증 코퍼스로 쓴다.
불일치는 우리가 틀렸다는 뜻이 아니라 둘 중 하나가 틀렸다는 뜻이고, 황경 잔차가 작은 쪽이 이긴다.

1. 절기는 1900~2100 전 구간을 Skyfield 와 JPL DE440s 로 계산한다.
   태양 겉보기 황경이 15도의 배수가 되는 순간을 이분법으로 찾는다.
   ADR 0006 이 금지한 "근사 공식" 은 절기를 대략 매월 4일과 19일로 보는 식을 말하며,
   정의를 그대로 푸는 계산은 여기 해당하지 않는다.
2. 2000~2028 도 계산값을 싣는다. KASI 값으로 채우면 2029년에서 산출 방식이 바뀌는 이음솔기가 생긴다.
3. 계산값과 KASI 를 대조해 불일치를 자동 분류한다. 판정 규칙은 아래와 같다.
   양쪽 잔차가 30초 봉투 안이면 어느 쪽도 틀리지 않은 것으로 보고 통과시킨다.
   봉투 밖이면 `kasi-corrections.json` 에 근거와 함께 등재되어야 통과한다.
   등재되지 않은 불일치가 있으면 검증이 실패한다.
4. 존재하지 않는 시각은 자동 보정하지 않는다. `17:60` 이 18:00 인지 17:06 오타인지 알 수 없다.
   격리해 정정 목록에 남기고 계산값을 쓴다.
5. 정답지가 없는 1900\~1999 와 2029\~2100 은 자체 정합성 검사로 본다.
   연도별 24개, 시각 순단조, 황경 15도 진행, 인접 간격 14.5~15.9일,
   간격의 연속성, 황경 잔차 0.1각초 미만, 춘분 주기 365.2422일이다.
6. 데이터는 `apps/web/src/lib/saju/data/` 아래 순수 `.ts` 모듈로 두고 값이 PR diff 에서 읽히게 한다.
   담는 방법은 건수가 정한다.
   절기 4,824건은 압축 바이너리를 base64 로 담고, base64 가 diff 로 읽히지 않으므로
   같은 내용을 사람이 읽는 JSON 으로도 커밋하고 테스트가 일치를 단언한다.
   음력 151행은 숫자 리터럴로 담는다. 그 자체가 diff 로 읽히므로 사본을 두지 않는다.
7. 지원 범위는 양력 입력 1900~2100, 음력 입력 1900년 1월 1일부터 2050년 11월 30일까지다.
   음력 상한이 낮고 해 중간에서 끊기는 것은 KASI 음력 데이터가 그 달에서 끝나기 때문이다.
   범위 밖 입력은 계산하지 않고 거부하며 지원 범위를 안내한다.
   상한이 12월이 아니라 11월인 것은 2026-08-14 에 전 구간을 덤프해 확인했다.
   이 항목은 처음에 "1900~2050" 으로 적혀 있었고 결정이 아니라 실측이 그것을 좁혔다.
8. 2029년 이후 절기에는 잠정 표시를 둔다. ΔT 가 예측값이라 나중에 KASI 발표와 달라질 수 있다.
9. 일진은 번들하지 않는다. 일주는 `(율리우스 적일 + 49) mod 60` 으로 계산하고
   KASI 일진은 검증 케이스의 기대값으로만 쓴다.
   조회로 대신하면 일주에 계산이 없어져 검증할 대상이 사라진다.
10. 음력은 자체 산출 알고리즘을 만들지 않는다. ADR 0006 의 결정을 그대로 유지한다.
    음력 2050년 12월 이후 입력은 지원하지 않는다.

## 이유

크기가 문제되지 않는다. 4,824건을 uint32 기준점 하나와 uint16 차이로 담아 9.4KB 이고
base64 로 12.6KB 다. 모듈 전체가 14.8KB 다. 지금 SSR 빌드의 라우터 청크 하나가 673KB 인 것과
비교하면 번들에서 존재감이 없다. 부분 조회로 아낄 것이 없다.

계산이 재현된다. [ADR 0013](0013-saju-engine-purity-enforcement.md) 의 근거가 재현 가능한 계산인데,
KASI 를 실시간으로 부르면 장애 때 계산이 멈추고 응답 형식이 바뀌면 결과가 조용히 달라진다.

엔진 순수성을 유지한다. ADR 0013 이 허용한 예외는 데이터 모듈이지 클라이언트가 아니다.
base64 를 담은 `.ts` 는 순수 JS 모듈이라 번들러 설정도 실행 환경 의존도 없다.
`.bin` 파일을 두면 Vite 의 `?arraybuffer` 같은 번들러 전용 import 가 필요해 그 조건이 깨진다.

생년월일이 밖으로 나가지 않는다. 절기 조회는 연도만 보내지만 음력 변환은 생년월일 그 자체를 보낸다.

서비스 키가 배포물에 없다. 덤프할 때만 쓰므로 Vercel 환경변수에 등록할 것이 없다.

Skyfield 를 고른 것은 실측 결과다. astronomy-engine 과 같은 696건을 계산해 대조했더니
KASI 와의 일치가 Skyfield 659건, astronomy-engine 551건이었다.
두 구현의 차이가 최대 56초, 중앙값 9초였고, 이는 절단된 태양 위치 이론의 정밀도 한계에 해당한다.
황경 1각초가 시간으로 약 24초이므로 분 단위 판정에는 부족하다.

자체 정합성 검사에 값이 있다는 것도 실측으로 확인했다.
KASI 데이터에 같은 검사를 돌리자 간격 이상이 대한 2011 을 정확히 지목했다.
외부 출처 없이 오류를 찾을 수 있다는 뜻이고, 정답지가 없는 구간에 쓸 유일한 수단이다.

JSON 을 함께 두는 것은 리뷰 때문이다. 바이너리만 커밋하면 데이터가 잘못 들어가도
PR 에서 diff 를 읽을 수 없다. 값이 틀려도 프로그램은 멀쩡히 돌고 화면에는 여덟 글자가 그대로 뜬다.
지켜야 하는 것은 이 읽힘이지 base64 라는 수단이 아니다.
음력표를 리터럴로 담은 것은 151행이 그 자체로 읽히기 때문이고, 사본을 두면 같은 값이 두 벌이 된다.

## 트레이드오프 / 대안

- 대안: 백엔드에서 런타임에 KASI 를 호출한다. 연도 범위 제한이 없고 갱신도 필요 없다.
  대신 계산이 외부 서비스의 가용성과 응답 형식에 묶인다.
  [ADR 0011](0011-single-prompt-no-streaming.md) 이 Gemini 응답 시간을 미확인 항목으로 두고 있는데
  거기에 KASI 왕복과 콜드스타트가 더해진다. 개발계정 일 10,000건 제한도 걸린다.
  앱이 오프라인에서 아무것도 못 하게 되는 것은
  [ADR 0003](0003-spa-bundle-for-app.md) 의 자기완결적 SPA 번들 전제와 어긋난다.
  무엇보다 이번에 확인한 KASI 데이터 결함이 그대로 결과에 들어온다.
- 대안: astronomy-engine 을 쓴다. 순수 JS 라 파이썬 의존이 없고 스택에 맞는다.
  696건 대조에서 551건만 일치해 탈락했다. 정밀도가 분 단위 절기 판정에 미치지 못한다.
- 대안: 2000~2028 은 KASI 발표값을 싣고 나머지만 계산한다.
  사용자가 다른 만세력과 비교했을 때 값이 같다는 이점이 있다.
  대신 2029년에서 출처가 바뀌는 이음솔기가 생기고, 33건에서 계산값과 1분씩 어긋난 채로 남는다.
  전 구간을 한 방식으로 산출하는 쪽을 택했다.
- 대안: 지원 범위를 KASI 가 주는 2000~2028 로 줄인다. 데이터에 맞추는 것이지만
  1960년대생을 다루지 못해 서비스가 성립하지 않는다.
- 파이썬 의존이 생긴다. pnpm 모노레포에 `apps/web/scripts/.venv` 와 31MB 짜리 천체력 파일이 들어온다.
  둘 다 gitignore 대상이고 생성 시점에만 필요하지만, 데이터를 다시 뜨려면 파이썬을 설치해야 한다.
- 지원 연도가 고정된다. 2100년 이후는 데이터를 다시 떠서 범위를 늘려야 한다.
  1900년 이전 출생자는 지원하지 않는다.
- 2029년 이후는 ΔT 가 예측값이다. 나중에 KASI 발표와 달라질 수 있고, 그때 값을 갱신해야 한다.
  과거 구간은 ΔT 가 관측으로 확정되어 있어 이 위험이 없다.
- 바이너리와 JSON 두 벌을 유지한다. 일치 검사를 테스트로 강제하지 않으면 두 벌이 갈라진다.
- KASI 오류를 우리가 판정해 덮어쓴다. 국가기관 데이터를 임의로 고치는 것으로 보일 수 있어
  정정 목록에 잔차와 간격 이상까지 근거로 남긴다.

## 영향

- 계산 엔진이 `data/solar-terms.ts` 를 상대 경로로 import 한다.
  `no-restricted-imports` 의 예외를 `!./**`, `!../**` 로 넓혀야 한다.
  `!./*` 는 한 단계만 허용해서 하위 디렉토리의 모듈이 걸린다.
- 입력 검증에 범위 확인이 들어간다. 양력과 음력의 상한이 다르므로 따로 본다.
  음력은 연도만으로 판정되지 않는다. 상한이 2050년 11월 30일이라 달과 일까지 본다.
- [docs/05-saju-domain-rules.md](../05-saju-domain-rules.md) 의 지원 연도 범위가 확정된다.
  CLAUDE.md 의 미정 목록에서 빠진다.
- 검증 케이스의 `blockedBy` 중 절기 시각을 기다리던 것들이 풀린다.
  2024년 입춘이 KST 02-04 17:27 로 확정되어 입춘 경계 케이스 둘을 채울 수 있다.
- 일주 앵커는 KASI 음양력 API 의 일진으로 대조한다.
  포스텔러와 KASI 두 곳이 되어 검증 케이스의 출처 두 곳 조건을 채운다.
- 절입 시각 근처에 태어난 경우 화면에 그 사실을 표시해야 한다.
  절기 시각이 몇 초 틀려도 대부분은 영향이 없고 경계 근처에서만 년주나 월주가 뒤집힌다.
  기준값은 아직 정하지 않았다.
- KASI 에 데이터 오류를 신고할 근거가 생겼다. 신고 여부는 정하지 않았다.
