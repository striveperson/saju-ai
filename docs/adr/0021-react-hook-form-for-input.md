# ADR 0021. 입력 폼을 react-hook-form 으로 든다

- 상태: 채택(Accepted)
- 날짜: 2026-08-16

## 배경

[docs/03](../03-frontend-rules.md) 8장이 폼 라이브러리의 선택을 미뤄 두고 있었다.
"항목이 늘어 필드 단위 구독이 필요해지면 폼 라이브러리를 쓴다.
어느 것을 쓸지는 아직 정하지 않았다. 지금은 `useState` 로 든다."

입력 지면의 `useState` 가 일곱 개까지 늘었다.
이름, 성별, 양력음력, 날짜, 시각, 윤달, 출생지에 오류 상태 하나가 더 붙어 있었고,
검증 결과를 `BirthError` 라는 자체 타입으로 들고 다녔다.
값과 오류를 따로 든 탓에 지우는 자리를 세 군데에 흩어 놓게 됐다.

여기에 구분자 자동 입력이 더해진다. 날짜에 `-` 를, 시각에 `:` 를 치는 대로 넣는다.
입력마다 값을 바꿔 쓰는 자리가 생기므로 값의 출처를 한 곳으로 모을 이유가 하나 늘었다.

## 결정

`react-hook-form` 7.85.0 을 `apps/web` 의 dependency 로 정확한 버전에 고정한다.
입력 지면의 폼 상태 일곱을 `useForm` 하나로 옮긴다.

1. 검증 규칙은 `useController` 의 `rules.validate` 에 단다.
   규칙 본문은 기존 `parseDate` 와 `parseTime` 을 그대로 부른다.
   판정을 두 벌로 만들지 않는다.
2. `@hookform/resolvers` 와 zod 스키마를 붙이지 않는다.
   [docs/03](../03-frontend-rules.md) 4장이 제어 컴포넌트의 값을 경계 밖으로 두고 있고,
   규칙이 이미 순수 함수로 있어 스키마가 그것을 한 번 더 적는 자리가 된다.
3. 날짜와 시각만 `useController` 로 등록한다. 나머지 넷은 `setValue` 와 `watch` 로 든다.
   입력칸이 없거나(출생지) 값이 틀릴 수 없는(성별, 양력음력, 윤달) 것들이다.
4. `reValidateMode` 를 `onSubmit` 으로 둔다. 기본값인 `onChange` 를 쓰지 않는다.
5. 구분자 마스킹은 폼이 아니라 `utils/birth.ts` 의 순수 함수 둘이 한다.
   `BirthFields` 가 입력마다 부르고, 폼에는 마스킹을 거친 값만 들어간다.
6. 제출 버튼은 그대로 넷이 다 차야 열린다.
   이름과 출생지의 필수 규칙을 폼에 적지 않은 것이 이 때문이다. 아래 트레이드오프에 있다.

## 이유

react-hook-form 을 고른 이유는 무게다. 런타임 의존이 0 이고 gzip 9KB 남짓이라
[ADR 0003](0003-spa-bundle-for-app.md) 이 Capacitor 에 넣기로 한 SPA 번들을 거의 늘리지 않는다.
React 19 와 React Compiler 를 함께 쓴 사례가 충분하다는 것도 본다.

3항으로 등록 방식을 가른 것은 `BirthFields` 를 라이브러리에서 떼어 두기 위해서다.
그 컴포넌트는 값과 콜백만 받는 제어 컴포넌트로 남고, `Controller` 를 그 안에 넣지 않는다.
목업과 대조할 때 읽어야 할 것이 늘지 않는다.

4항은 지우는 시점을 지키려는 것이다. `onChange` 되검증은 값이 유효해져야 문구를 지우는데,
날짜 칸은 마스킹이 여덟 자리에서 끊으므로 틀린 날짜에 숫자를 더 쳐도 값이 그대로다.
고치기 시작했는데 문구가 남아 있게 된다. 제출 시점 되검증에 `clearErrors` 를 붙이면
치는 즉시 지워지고, 이것이 옮겨 오기 전의 동작이다.

5항으로 마스킹을 밖에 둔 것은 그것이 표기이지 검증이 아니어서다.
`parseDate` 는 구분자를 가리지 않아 마스킹이 없어도 통과한다.
순수 함수라 폼 없이 단위 테스트로 확인한다.

## 트레이드오프 / 대안

- 이름과 출생지에는 규칙을 달지 않았다. 제출 버튼이 넷이 다 차야 열려서
  빈 값으로 제출되는 경로가 없고, 도달하지 않는 규칙과 문구 자리가 남는다
  ([docs/06](../06-code-working-rules.md) 2장). 버튼을 항상 열어 두는 쪽으로 바꾸면
  그때 규칙을 단다. 그 전까지 이름이 비었을 때 사용자가 보는 것은 잠긴 버튼뿐이고,
  왜 잠겼는지는 화면이 말하지 않는다.
- 의존이 하나 늘었다. 판올림을 따라가야 하고 공급망 표면이 그만큼 넓어진다.
- 제출 처리기가 값을 한 번 더 파싱한다. `validate` 가 참과 거짓만 돌려주고
  파싱한 값을 버리기 때문이다. 규칙이 이미 통과시킨 값이라 두 번째 파싱은 항상 성공하는데,
  타입을 좁히려고 도달하지 않는 분기를 하나 두게 된다.
- 대안: `useState` 를 유지하고 마스킹만 붙인다. 의존이 안 늘고 지금 코드가 그대로 간다.
  상태 일곱과 오류 하나를 손으로 맞추는 일이 남고, 항목이 더 늘면 같은 논의를 다시 한다.
- 대안: TanStack Form 을 쓴다. 저장소가 이미 TanStack 을 넷 쓰고 있어 결이 맞고
  `@tanstack/intent` 로 공식 스킬을 읽을 수 있다. 고르지 않은 것은 react-hook-form 쪽이
  같은 일에 API 가 적고, 이 폼이 필드 일곱짜리라 프레임워크 통합에서 얻을 것이 없어서다.
  폼이 여러 지면으로 늘고 서버 검증이 붙으면 그때 다시 본다.
- 대안: zod 스키마와 리졸버를 붙인다. 규칙이 한 곳에 모이고 타입이 값에서 나온다.
  `parseDate` 가 양력과 음력에 다른 잣대를 대고 음력은 형식만 보므로
  스키마로 옮기면 `superRefine` 안에서 같은 함수를 부르게 된다. 층만 하나 는다.

## 영향

- [docs/03](../03-frontend-rules.md) 8장의 "어느 것을 쓸지는 아직 정하지 않았다" 가 이것으로 닫힌다.
- 날짜 칸의 표기가 `1995/01/27` 에서 `1995-01-27` 로 바뀐다.
  목업 `input-screen.html` 의 placeholder 와 마스킹 흉내가 함께 바뀌었다.
  `parseDate` 는 구분자를 가리지 않아 읽는 쪽은 그대로다.
- 아직 만들지 않은 입력 항목이 이 결정을 물려받는다.
  시 미상 토글과 야자시 정책 토글이 그것이고, 둘 다 자리를 감춰 둔 상태다.
