# ADR 0010. Supabase 로 인증, DB, 권한을 함께 처리한다

- 상태: 채택(Accepted)
- 날짜: 2026-08-05

## 배경

[ADR 0008](0008-social-login-server-storage.md) 에서 소셜 로그인과 서버 저장을 택했다.
인증 공급자, 세션 관리, 데이터베이스, 권한 검증을 무엇으로 할지 정해야 한다.

한국 서비스라 카카오 로그인이 사실상 필수다.
[ADR 0002](0002-tanstack-start-capacitor-shell.md) 의 Capacitor 셸 때문에
앱에서의 OAuth 흐름도 함께 풀어야 한다.

## 결정

1. Supabase Auth 로 소셜 로그인을, Supabase Postgres 로 데이터를, RLS 로 행 단위 권한을 처리한다.
2. 소셜 공급자는 카카오를 주력으로 하고 Apple 로그인을 함께 제공한다. 구글은 선택이다.
3. Capacitor 웹뷰 안에서 공급자 인증 화면을 직접 열지 않는다.
   시스템 브라우저(`@capacitor/browser`)를 띄우고 PKCE 로 진행한 뒤 커스텀 스킴 딥링크로 복귀한다.
4. 웹은 SSR 세션 쿠키를 쓰고 앱은 토큰을 쓴다. 두 경로를 모두 다룬다.
5. RLS 정책은 테이블마다 명시적으로 작성하고 테스트로 검증한다.

Apple 로그인은 취향이 아니라 의무다.
iOS 앱이 카카오나 구글 로그인을 제공하면 App Store 지침 4.8 이 Apple 로그인의 동등 제공을 요구한다.

앱에서 시스템 브라우저를 쓰는 것도 선택이 아니다.
구글은 내장 웹뷰에서 뜬 인증 요청을 `disallowed_useragent` 로 차단한다.

## 이유

- Supabase Auth 가 카카오와 Apple 을 공식 공급자로 지원하고 PKCE 와 딥링크 흐름이 문서화되어 있다.
- 혼자 운영하는 규모에서 인증, DB, 권한을 각각 붙이면 통합 지점마다 비용이 든다.
  한 곳에서 가져오면 그 비용이 사라진다.
- RLS 는 권한을 데이터베이스 계층에 두므로 API 라우트를 하나 빠뜨려도 데이터가 새지 않는다.

## 트레이드오프 / 대안

- 대안 1: better-auth 와 Neon Postgres 를 직접 조합한다. 종속이 없고 스키마를 완전히 통제하지만
  앱 OAuth 복귀 흐름과 토큰 만료 처리를 직접 설계해야 한다.
- 대안 2: Firebase Auth 와 Firestore. Capacitor 네이티브 플러그인이 잘 갖춰져 있고 푸시도 같은 생태계지만
  카카오를 공식 지원하지 않아 커스텀 토큰 계층을 얹어야 하고,
  사주 프로필과 공유 링크의 관계가 문서형 DB 와 맞지 않는다.
- 벤더 종속도가 높다. 인증과 DB 를 동시에 옮겨야 하므로 이탈 비용이 크다.
- RLS 정책을 잘못 쓰면 타인 데이터가 노출된다. 정책 자체가 테스트 대상이다.
- 공유 링크는 인증 없이 열리므로 RLS 를 우회하는 서버 키 조회 경로가 필요하다.
  이 경로가 정책의 구멍이 되지 않도록 조회 대상을 활성 링크로 한정한다.

## 영향

- 스키마 초안은 아래와 같다.

| 테이블 | 접근 정책 |
|--------|-----------|
| `saju_profiles` | RLS. 본인 행만 읽고 쓴다 |
| `share_links` | RLS 로 본인 관리. 공개 조회는 서버 키로 활성 링크만 |
| `interpretation_cache` | 사용자 식별 정보 없음. 해시 키로만 조회 |

- 앱은 커스텀 스킴(`saju://auth/callback`)을 등록해야 한다. iOS 와 Android 양쪽에 설정이 필요하다.
- 로그인 없이 계산까지 되는 경로가 있으므로 인증 상태에 따라 화면이 갈린다
  ([ADR 0008](0008-social-login-server-storage.md)).
