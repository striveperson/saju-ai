# ADR 0002. TanStack Start 단일 웹 앱 + Capacitor 모바일 셸

- 상태: 채택(Accepted)
- 날짜: 2026-08-05

## 배경

사주 서비스를 웹과 모바일 앱으로 낸다. 클라이언트를 몇 개로 볼 것인지,
서버 로직을 어디에 둘 것인지, 앱을 얼마나 네이티브로 만들 것인지를 정해야 한다.

## 결정

1. 제품의 전부를 TanStack Start 로 만든다. SSR, 라우팅, 서버 로직을 이 앱 하나가 담당한다.
   별도 백엔드 서버를 두지 않는다.
2. 모바일은 Capacitor 로 웹을 감싼 셸이다. 네이티브 화면은 만들지 않는다.
3. 네이티브 기능은 푸시 알림, 스플래시, 딥링크 정도를 플러그인으로 붙인다.
4. `apps/mobile` 에는 비즈니스 로직을 넣지 않는다.

## 이유

- 클라이언트가 실질적으로 하나이므로 화면을 두 번 만들지 않아도 되고 API 계약을 이중 관리할 필요가 없다.
- 전 구간 TypeScript 로 통일된다. 사주 계산 엔진을 서버와 클라이언트가 같은 코드로 쓴다.
- TanStack Query 는 form-flow 에서 이미 쓰던 것이라 학습 비용이 없다.
- 사주 계산은 순수 함수라 클라이언트에서 완결된다. 서버가 담당할 일이 AI 해석과 저장뿐이라
  서버를 별도 프로세스로 분리할 이유가 없다.

## 트레이드오프 / 대안

- 대안 1: React Native 로 네이티브 앱을 만든다. 앱다운 UX 를 얻지만 화면을 두 번 만들어야 하고
  계산 엔진을 공유 패키지로 빼야 한다. 웹 껍데기로 충분하다고 판단해 채택하지 않았다.
- 대안 2: React + Spring Boot 분리(form-flow 방식). 익숙한 스택이지만
  [ADR 0001](0001-monorepo-pnpm-workspaces.md) 의 이점을 상쇄하고 타입 계약을 이중 관리하게 된다.
- 네이티브다운 UX(제스처, 화면 전환 감)는 포기한다.
- App Store 심사 지침 4.2(최소 기능)에서 단순 웹사이트 래퍼로 반려될 위험이 있다.
  네이티브 가치를 하나 이상 확보해야 한다. 오프라인 사주 계산([ADR 0003](0003-spa-bundle-for-app.md))과
  "오늘의 운세" 푸시 알림이 그 역할을 한다.
- TanStack Start 는 SSR 을 전제로 하므로 Capacitor 가 웹 자산을 어떻게 로드할지가 자명하지 않다.
  [ADR 0003](0003-spa-bundle-for-app.md) 에서 다룬다.

## 영향

- 배포 단위는 `apps/web` 과 `apps/mobile` 둘이다.
- `apps/mobile` 에 비즈니스 로직을 넣지 않는다는 원칙을 CLAUDE.md 제약으로 못 박는다.
- 인증은 웹 세션과 모바일 토큰 두 경로를 모두 다뤄야 한다([ADR 0010](0010-supabase-auth-and-db.md)).
- 앱 릴리스가 스토어 심사를 타므로 웹과 배포 주기가 어긋난다([ADR 0012](0012-vercel-deploy.md)).
