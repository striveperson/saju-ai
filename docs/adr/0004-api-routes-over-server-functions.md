# ADR 0004. 데이터 접근은 명시적 API 라우트로 통일한다

- 상태: 채택(Accepted)
- 날짜: 2026-08-05

## 배경

TanStack Start 는 서버 함수(`createServerFn`)와 서버 라우트(HTTP 엔드포인트) 두 가지 서버 진입점을 제공한다.
서버 함수는 클라이언트에서 호출하면 자동으로 HTTP 요청으로 바뀌는데, 그 요청이 상대 경로로 나간다.

[ADR 0003](0003-spa-bundle-for-app.md) 에서 앱을 SPA 정적 번들로 만들기로 했으므로
앱은 `capacitor://localhost` 오리진에서 뜬다. 상대 경로 호출은 서버로 나가지 않는다.

## 결정

1. 서버 호출은 TanStack Start 의 서버 라우트로 노출한 HTTP 엔드포인트로만 한다.
2. 요청·응답 스키마는 Zod 로 한 곳에 정의하고 서버가 파싱한다.
3. 웹과 앱이 같은 엔드포인트를 쓴다.
4. 서버 함수(`createServerFn`)는 데이터 경로로 쓰지 않는다.
5. API base URL 은 환경별로 주입한다. 웹은 상대 경로, 앱은 배포된 웹의 절대 URL.

## 이유

- 앱이 절대 URL 로 호출해야 하고, 그러려면 base URL 을 주입할 수 있는 명시적 엔드포인트여야 한다.
- 웹과 앱이 서로 다른 호출 방식을 쓰면 한쪽에서만 재현되는 버그가 생긴다.
  진입점이 하나면 그런 버그가 구조적으로 발생하지 않는다.
- 엔드포인트가 명시적이면 문서화하기 쉽고 계약을 검증하기 쉽다.

## 트레이드오프 / 대안

- 대안 1: tRPC 를 도입해 웹과 앱 모두 타입 안전 RPC 로 호출한다.
  계약 불일치가 컴파일 에러로 잡히지만 의존성과 학습 비용이 늘고,
  엔드포인트가 5~8 개 규모인 이 프로젝트에는 과하다.
- 대안 2: 웹은 서버 함수, 앱은 REST 를 병행한다. 웹의 DX 를 살리지만
  진입점이 둘이 되어 검증·인증 코드가 이중 관리된다.
- 서버 함수가 주는 자동 타입 연결을 포기하고 Zod 스키마로 수동 결방한다.
  form-flow 의 `api-contract-checker` 에이전트를 이식해 보완한다.

## 영향

- 엔드포인트는 많아야 5~8 개로 예상된다. 사주 계산 자체는 API 가 아니라 클라이언트 로컬 실행이다.
  서버가 필요한 것은 AI 해석 생성, 해석 캐시 조회, 사주 프로필 저장·조회, 공유 링크 관리 정도다.
- CORS 설정이 필요하다. 앱 오리진을 허용 목록에 넣는다.
- API 명세 문서를 별도로 유지한다.
