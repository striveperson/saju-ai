# 00. 문서 작성 가이드

> 이 문서는 saju-ai 프로젝트 문서를 어떻게 쓰고 관리할지를 정의한다. 새 문서를 추가하거나 기존 문서를 고칠 때 이 규칙을 따른다.

## 1. 문서는 어디에 두는가

- 모든 프로젝트 문서는 저장소 루트의 `docs/`에 둔다.
- 특정 모듈에만 해당하는 짧은 설명은 해당 폴더의 `README.md`로 둔다.
  - 예) `apps/web/src/lib/saju/README.md`
- "왜 이렇게 결정했는가"를 남기는 의사결정 기록은 `docs/adr/`(Architecture Decision Record)에 번호순으로 둔다.

```
docs/
├── 00-documentation-guide.md
├── 01-overview.md
├── 02-architecture.md
├── 03-frontend-rules.md         화면 규칙 SSOT
├── 05-saju-domain-rules.md      사주 도메인 SSOT
├── 06-code-working-rules.md     코드 작업 방식
├── 07-sinsal-rules.md           신살 SSOT
└── adr/
    └── 0001-monorepo-pnpm-workspaces.md ~ 0016-true-solar-time-always-applied.md
```

### 1.1 무엇을 기준으로 쪼개는가

길이가 아니라 참조 관계로 쪼갠다. 서로를 자주 참조하는 규칙은 한 문서에 둔다.
길이 규칙(5장)보다 이쪽이 우선한다.

`05-saju-domain-rules.md` 가 그 예다. 스크롤 5번을 넘지만 쪼개지 않는다.
입력 시각에서 팔자와 운으로 가는 한 줄기라 장 사이 대조가 잦고,
검증기가 대운 하나를 확인할 때도 머리말부터 10장까지 열어 본다.
파일이 갈리면 그 대조가 grep 으로 밀린다.

신살을 `07-sinsal-rules.md` 로 뗀 것은 반대 경우다.
완성된 팔자를 받는 판정이라 05 의 어느 장도 참조하지 않는다.

부피가 문제면 쪼개기 전에 있을 자리가 아닌 것을 먼저 뺀다.
기각 기록과 결정의 경위는 ADR 이 맡는다.

## 2. 파일 네이밍 규칙

- 소문자 + 하이픈(`kebab-case`)을 사용한다. `saju-domain-rules.md` 는 맞고 `SajuDomainRules.md` 는 틀리다.
- 읽는 순서가 중요한 문서는 앞에 2자리 번호를 붙인다. (`01-overview.md`)
- ADR 은 4자리 번호 + 요약을 붙인다. (`0007-strength-five-grade-model.md`)
- 루트 안내 문서만 대문자 `README.md`로 둔다.

## 3. 문서 한 편의 표준 구조

```markdown
# NN. 문서 제목

> 한두 문장으로 이 문서가 무엇을 다루는지 요약.

## 1. 큰 주제
### 1.1 세부 주제
- 핵심을 불릿으로
- 코드/표/다이어그램으로 보강
```

- 제목(`#`)은 문서당 하나.
- 섹션은 `##`, 하위는 `###`까지만. 4단계 이상 들어가면 문서를 쪼갠다.

## 4. ADR 작성 규칙

ADR 은 아래 형식을 지킨다. 이 프로젝트의 모든 ADR 이 같은 골격을 갖는다.

```markdown
# ADR NNNN. 결정을 한 문장으로

- 상태: 채택(Accepted) | 대체됨(Superseded by ADR NNNN) | 폐기(Deprecated)
- 날짜: YYYY-MM-DD

## 배경
## 결정
## 이유
## 트레이드오프 / 대안
## 영향
```

- 결정을 바꿀 때는 기존 ADR 을 수정하지 않고 새 ADR 을 쓴 뒤 기존 것의 상태를 `대체됨`으로 바꾼다.
- 채택하지 않기로 한 것도 기록한다. 같은 논의가 반복되는 것을 막는 것이 ADR 의 주된 값어치다.
- 큰 구조·기술 결정은 코드보다 ADR 을 먼저 쓴다.

## 5. 마크다운 스타일 규칙

문서(`*.md`)와 Claude 의 마크다운 답변 모두에 적용한다.

| 항목 | 규칙 |
|------|------|
| 코드 블록 | 항상 언어 지정 (` ```ts `, ` ```sql `, ` ```bash `) |
| 파일 경로 | 코드 블록 첫 줄에 주석으로 경로 표기 |
| 표 | 비교·명세·매핑에 적극 사용 |
| 다이어그램 | [Mermaid](https://mermaid.js.org/) 사용 (GitHub 에서 바로 렌더링됨) |
| 링크 | 문서 간 이동은 상대 경로 링크 |
| 용어 | 도메인 용어는 [`01-overview.md`](01-overview.md) 용어집, 계산 규칙은 [`05-saju-domain-rules.md`](05-saju-domain-rules.md) 와 일치시킨다 |
| 길이 | 한 문서가 너무 길어지면(스크롤 5번 이상) 분리. 쪼개는 기준은 1.1 이 우선한다 |

### 5.1 강조와 기호

- 굵은 강조(`**`)는 어겨서는 안 되는 규칙에만 쓴다. 장식이나 습관으로 쓰지 않는다.
  한 문서에 두세 번을 넘기면 이미 남용이다.
- 번호 목록(`1.` `2.` `3.`) 안에서는 굵은 강조를 쓰지 않는다.
  번호가 이미 구분을 하고 있으므로 강조가 겹친다.
- 이모지는 쓰지 않는다. 상태 기호(✓ ✗ ⭕ ❌ ⚠)도 표나 다이어그램에서 의미가 분명할 때만 쓰고, <!-- md-allow -->
  본문 문장에는 넣지 않는다.
- em dash(—)를 쓰지 않는다. 쉼표, 콜론, 괄호, 하이픈(-)으로 대체한다. <!-- md-allow -->
- 화살표(→)는 순서나 변환을 나타낼 때만 쓴다. 문장을 이어붙이는 용도로 쓰지 않는다.
- 취소선을 쓰지 않는다. 지울 내용이면 지운다. 무엇을 지웠는지는 git 이 기억한다.
  범위 표기(`1900~2100`)가 취소선으로 바뀌어 있으면 손상된 것이므로 되돌린다.
- 한 줄에 물결표를 둘 이상 남기지 않는다. GFM 은 물결표 하나짜리도 취소선 구분자로 읽어
  둘을 짝지어 그 사이를 지운다. 범위 표기가 한 문장에 둘 오면 여기 걸린다.
  범위는 `1900\~2100` 처럼 escape 하고, 물결표 자체를 보여야 하면 백틱으로 감싼다.

이 규칙들은 `.claude/hooks/md-style-guard.sh` 가 파일 저장 시 검사한다.
규칙 자체를 설명하느라 금지된 문자를 써야 하는 줄에는 `<!-- md-allow -->` 를 붙이면 통과한다.
코드 블록 안은 검사하지 않는다.

마크다운은 `oxfmt` 에 넘기지 않는다.
범위 표기의 물결표 둘을 짝지어 취소선으로 바꾸면서, 손대지 않은 줄까지 조용히 망가뜨린다.
`.oxfmtrc.json` 과 `format-file.sh` 양쪽에서 제외한다.

### 5.2 문장 규칙

기계가 찍어낸 듯한 문서를 만들지 않기 위한 규칙이다.
정규식으로 검사할 수 없어 훅이 잡지 못한다.
고치기 전후 예시와 확인 목록은 `.claude/skills/writing-style/SKILL.md` 에 있다.

- 한 문장에 한 가지만 담는다. 문장이 세 줄을 넘으면 자른다.
- 근거 없는 형용사를 쓰지 않는다. 강력한, 혁신적인, 원활한, 매끄러운, 최적의, 손쉬운 같은 말은
  아무것도 설명하지 않는다. 대신 무엇이 어떻게 되는지를 쓴다.
- 같은 문장 구조를 연달아 반복하지 않는다.
  불릿 전부가 "무엇을 무엇한다" 꼴이면 읽는 사람이 내용을 구분하지 못한다.
- 세 항목을 기계적으로 나열하는 습관을 경계한다. 두 개면 두 개만 쓴다.
- 메타 서술을 쓰지 않는다. "중요한 점은", "주목할 만한 것은", "다음과 같습니다" 는 지운다.
- 문서 끝에 앞 내용을 되풀이하는 요약 절을 붙이지 않는다.
- 번역투를 줄인다. `~에 대한`, `~를 통해`, `~에 있어서` 를 우리말 어순으로 고친다.
- 결정을 적을 때는 단정한다. `~할 수 있습니다`, `~하는 것이 좋습니다` 대신 `~한다` 로 쓴다.
  확정되지 않은 것은 확정되지 않았다고 명시한다.
- 트레이드오프를 적을 때 좋은 점만 쓰지 않는다. 포기한 것을 반드시 함께 적는다.

## 6. 문서를 최신으로 유지하는 규칙

1. 코드와 문서는 같은 PR 에서 바꾼다.
2. 사주 계산 규칙은 [`05-saju-domain-rules.md`](05-saju-domain-rules.md) 가 단일 진실 공급원(SSOT)이다.
   코드와 이 문서가 어긋나면 코드가 틀린 것으로 간주한다.
   문서가 틀렸다면 근거와 함께 문서를 먼저 고치고, 그 다음 코드를 고친다.
3. 문서 리뷰도 코드 리뷰처럼 PR 로 진행한다.

## 7. 문서 추가 체크리스트

- [ ] 코드 블록에 언어와 파일 경로가 있는가
- [ ] 용어가 용어집·SSOT 와 일치하는가
- [ ] em dash 와 이모지를 쓰지 않았는가
- [ ] 굵은 강조가 세 번 이하이고, 번호 목록 안에 강조가 없는가
- [ ] 근거 없는 형용사와 메타 서술을 지웠는가
- [ ] 트레이드오프에 포기한 것이 적혀 있는가
