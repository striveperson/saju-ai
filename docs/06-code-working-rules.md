# 06. 코드 작업 규칙

> Claude 가 이 저장소에서 코드를 고칠 때 지키는 작업 방식. 무엇을 지킬 것인가는 루트 [CLAUDE.md](../CLAUDE.md) 와 [05-saju-domain-rules.md](05-saju-domain-rules.md) 에 있고, 이 문서는 어떻게 작업할 것인가를 다룬다.

출처는 [andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills) 의 CLAUDE.md 다.
원문 네 절을 옮기고 이 저장소의 규약과 이어 붙였다.

속도보다 신중함 쪽으로 기운 규칙이다. 오타 수정이나 한 줄짜리 변경에까지 그대로 적용하지 않는다.

## 1. 짐작하지 않는다

구현을 시작하기 전에 할 일이다.

- 전제를 말로 적는다. 확신이 없으면 묻는다.
- 요청이 두 가지로 읽히면 둘 다 내놓는다. 하나를 조용히 고르지 않는다.
- 더 단순한 방법이 있으면 말한다. 근거가 있으면 요청에 반대한다.
- 막히는 지점이 있으면 멈추고, 무엇이 불분명한지 이름을 붙여 묻는다.

이 저장소에서는 도메인 규칙이 애매할 때가 여기 해당한다.
추측해서 구현하지 않고 근거를 찾거나 사용자에게 확인한다.

## 2. 요청받은 만큼만 만든다

문제를 푸는 최소한의 코드를 쓴다.

- 요청에 없는 기능을 얹지 않는다
- 한 번만 쓰이는 코드를 추상화하지 않는다
- 요청하지 않은 설정 가능성이나 확장 지점을 만들지 않는다
- 일어날 수 없는 상황에 예외 처리를 두지 않는다
- 200줄을 썼는데 50줄로 되는 일이면 다시 쓴다

기준은 하나다. 경력자가 보고 과하다고 할 코드면 과한 것이다.

## 3. 건드릴 것만 건드린다

기존 코드를 고칠 때 지킨다.

- 옆에 있는 코드, 주석, 포맷을 겸사겸사 손보지 않는다
- 망가지지 않은 것을 리팩터링하지 않는다
- 내 취향과 달라도 주변 코드의 스타일을 따른다
- 관련 없는 죽은 코드를 발견하면 말만 하고 지우지는 않는다

치우는 범위는 내가 만든 것까지다.
내 수정 때문에 쓰이지 않게 된 import, 변수, 함수는 지운다.
원래부터 죽어 있던 코드는 따로 요청받았을 때만 지운다.

확인하는 방법은 diff 의 모든 줄이 요청과 직접 이어지는지 보는 것이다.

## 4. 성공 조건을 먼저 정한다

작업을 검증 가능한 목표로 바꾼다.

| 받은 요청         | 바꾼 목표                                     |
| ----------------- | --------------------------------------------- |
| 검증을 추가해줘   | 잘못된 입력에 대한 테스트를 쓰고 통과시킨다   |
| 버그를 고쳐줘     | 버그를 재현하는 테스트를 먼저 쓰고 통과시킨다 |
| X 를 리팩터링해줘 | 전후로 테스트가 모두 통과하는지 확인한다      |

여러 단계로 나뉘는 작업은 계획을 먼저 짧게 적는다.

```
1. [단계] / 확인: [무엇으로 확인하는가]
2. [단계] / 확인: [무엇으로 확인하는가]
```

성공 조건이 분명하면 중간에 되묻지 않고 스스로 반복할 수 있다.
"동작하게 해줘" 정도의 조건은 매번 다시 물어야 한다.

표의 둘째 행은 루트 CLAUDE.md 의 "버그 수정은 재현 테스트를 먼저 쓴다" 와 같은 규칙이다.
계산 엔진은 여기에 더해 경계 케이스 테스트가 필수다.
필수 목록은 [05-saju-domain-rules.md](05-saju-domain-rules.md) 10장에 있다.

구현과 검증은 다른 단계에 둔다.
구현한 맥락에서 스스로 확인하면 방금 한 착각을 그대로 한 번 더 한다.
계산 엔진을 고쳤으면 `saju-engine-validator` 에이전트를 부른다.
그 에이전트는 diff 와 05 문서를 새로 읽어 대조만 하고 고치지는 않는다.

## 5. 지켜지고 있는지 보는 법

diff 에서 요청과 무관한 줄이 줄어든다.
과하게 만들어놓고 다시 쓰는 일이 줄어든다.
되묻는 질문이 실수를 낸 뒤가 아니라 구현 전에 나온다.
